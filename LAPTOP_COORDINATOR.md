# Laptop coordinator instructions

Use this setup only for the user's authorized task. Main coordinator and canonical research remain on the laptop. Read the current ATLAS execution specification, execution policy and round contract before scientific work. Do not treat the setup smoke test as an active research round.

1. Verify `atlas_team.team_status`. If tools are not loaded in this chat, use `python3 "/ABSOLUTE/PATH/TO/multi-node-codex/teamctl.py" call TOOL_NAME --file REQUEST.json`. `start`/`connect` are available on that CLI when needed. Do not place credentials in request files.
2. Select a unique shared run ID and use `laptop-coordinator` as your mailbox identity. Divide work into owned tasks. Use up to 16 native laptop workers (configure that laptop limit separately) and one coordinator per configured remote host, each with up to 16 native workers. With three remote hosts this is 64 workers plus four coordinators. All use the same MAG model/provider and account quotas. Do not create additional independent sessions to evade the limits.
3. Dispatch a bounded, reviewable task to each needed remote coordinator using `team_dispatch`, `host` set to a configured SSH alias (the example uses `dell1`, `dell2` and `spark1`), `project="atlas"`, and the same shared run ID. Omitted host selects `default_host`. Query `team_status` for the actual coordinator mailbox names. Include acceptance criteria, explicit native subagent delegation, dependencies, evidence requirements and deadlines. The remote snapshot path on each host is `REMOTE_HOME/.local/share/atlas-codex/projects/atlas`; snapshots may differ and may be older than current laptop research. Send changed context as versioned artifacts before dependent work. If this chat has stale tool schemas without `host`, use the CLI fallback in step 1 or reload the chat.
4. Give every worker a unique host-prefixed mailbox (for example `dell2:evidence-1`) and the shared run ID. Prefix host-specific tasks and artifacts too; use shared IDs only intentionally. Require atomic `team_task_claim` and `team_task_finish`. Require inbox checks between substantial steps and at task boundaries. During coordination waits use `team_inbox(wait_seconds=30)` or shorter; do not leave the coordinator blocked for more than 60 seconds. Native within-host collaboration remains available. Workers on any host may message any other host's worker through these shared inboxes.
5. Receive remote messages with `team_inbox(recipient="laptop-coordinator")`; acknowledge only after handling them. Read progress with `team_events` and retain its cursor. To update an active remote coordinator, use `team_message` with `steer=true` and recipient `remote-coordinator` (dell1), `remote-coordinator:dell2`, or `remote-coordinator:spark1`. Sending to a local/native worker does not wake it: arrange its inbox polling explicitly. No automatic messages are sent into other user-owned Codex chats.
6. Keep task claims and decisions in the shared store. Publish findings, counterexamples, dependencies, evidence provenance and uncertainty as versioned artifacts. Separate proposal and evaluation workers. Reconcile only reviewed changes into canonical laptop files. User retains scientific acceptance.
7. Track 1800-second phase deadlines. The bridge rejects expired claim completion but does not kill overdue processes. Checkpoint and interrupt overdue work. Inspect active remote threads with `team_status(refresh_remote=true)` before declaring a phase finished. Do not start detached background compute during a phase unless the user has separately authorized that lifecycle.
8. On disconnection, inspect status/events before retrying. Never redispatch work with an uncertain outcome. Resume or interrupt the recorded remote run after reconnecting. Supply both `run_id` and `host` to `team_interrupt`. `teamctl.py disconnect --host HOST` closes only that host; `teamctl.py stop` closes all three. Separately stop native local workers through native collaboration tools. A disconnected run blocks further dispatch only on its own host.

This bridge provides mailbox delivery and steering of the remote coordinator, not a single distributed native agent tree. Keep the laptop awake and the coordinator active/polling when frequent collaboration is required.
